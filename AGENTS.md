## pCloud MCP + generated skills

- API documentation: `references/pcloud-docs/` (fetched from docs.pcloud.com, one markdown file per page; regenerate with `python3 scripts/fetch_pcloud_docs.py references/pcloud-docs`).
- Authentication posture is non-OAuth: a static access token is read from `PCLOUD_ACCESS_TOKEN` (global env, exported in the shell rc; sourced from the rclone token store on this host) and sent as the `access_token` query parameter per the HTTP/JSON protocol. `PCLOUD_ACCESS_ID` is available from global env but is the application/access id, not a credential for this protocol.
- All requests go to `https://eapi.pcloud.com/<method>` (EU region for this account); every response carries `result` — `0` success, non-zero error with `error` message surfaced as MCP `isError`.
- 36 tools registered. The authoritative list, with titles, descriptions, and Zod input/output schemas, is `src/core/tools/index.ts` — that is the SSOT for what this server exposes. `deletefile` and `deletefolder` are intentionally separate. `resolve` wraps `stat` to give `{fileid|folderid, isfolder}` from a path. `find` is a BFS over `listfolder` (pCloud exposes no documented search endpoint). `copyfile` and `copyfolder` are server-side (no download+upload round trip). `downloadfile` is also server-side — pCloud fetches the URL(s) and stores them in the destination folder, no bytes cross the MCP server. `createuploadlink` creates a public upload link; `uploadtolink` POSTs a file to that link's code with no auth (link code is the credential). `revertrevision` reverts a file to an earlier revision (current contents are saved as a new revision). `getthumblink` / `getvideolink` / `getaudiolink` return pCloud-streaming URLs for images, video (FLV/x264), and audio (MP3 transcode). `getapiserver` / `currentserver` are no-auth introspection endpoints for choosing the closest API host and tracking upload progress. `createfolderifnotexists` is the idempotent version of `createfolder` (returns the existing folder instead of erroring 2004). `checksumfile` returns sha1 (always) + md5 (US region) / sha256 (EU region). `uploadfile` and `uploadtolink` share `src/core/http/upload.ts` for chunked reads and progress; progress notifications echo the request's `_meta.progressToken` (none emitted if the client did not ask) and are labeled `read`/`uploading` — read progress covers the local disk read only, since Bun's `FormData`/Blob still requires the full buffer for the single multipart POST. `readfile` streams the download and cancels at `maxBytes`; the signed download URL is never returned (short-lived credential).
- Run `bun run build` before `bun run start`; unit tests with `bun test`; MCP registration is workspace-only via `.mcp.json` at the repo root (and `.kimi-code/mcp.json` for the Kimi layer).
- Live pCloud quirk worth knowing: `trash_list`, `trash_restore`, `listrevisions`, `createuploadlink`, and `revertrevision` return `1000 Log in required` for this account even though the same token works for every other endpoint (verified with direct curl — not a tool bug). **Confirmed root cause for the trash family** (`trash_list`, `trash_restore`): token *provenance*, not scope — pCloud's OAuth tokens (`access_token=`) are silently rejected; only a legacy `/getauth` session token (sent as `auth=`) is accepted. There is no OAuth `scope` to widen — `oauth2_token` documents no scope parameter and returns none. This is an undocumented pCloud API limitation reproduced since 2020 (rclone #3853, closed as Known Problem; pCloud support never acknowledged). The JS SDK encodes the same split: `createClient(token, 'pcloud')` sends `auth=`, `createClient(token, 'oauth')` sends `access_token=`. **For `listrevisions`, `createuploadlink`, and `revertrevision` the same 1000 symptom is observed but the cause is unconfirmed** — see `references/pcloud-unresolved-notes.md` before asserting provenance for those three; the untruncated statement should remain a hypothesis until tested against a file with known revisions or a `/getauth` session token. All five tools stay in the surface in case a `PCLOUD_AUTH` session-token mode is ever wired; until then agents needing these workflows use the pCloud web UI. `deletepublink` returns `2027` for an unknown linkid (informative; idempotent in spirit but not literally). `getfilepublink` and `gettextfile` are "referrer restricted to pcloud.com" per docs.
- Live verification against the real pCloud API: `bun run scripts/live-mcp-e2e.ts` (requires `PCLOUD_ACCESS_TOKEN`; creates a temp folder + file, exercises upload/getfilelink/deletefile/deletefolderrecursive, cleans up after itself).
- After any change to `src/core/tools/*`: run `bun run typecheck && bun run build && bun test && bun run lint`, then `mcporter generate-cli --server pcloud` + `bun build pcloud.ts --target=bun --outfile=generated/pcloud-cli.js --minify` + `mcporter emit-ts pcloud --mode types --out generated/pcloud-types.d.ts` + `mcporter emit-ts pcloud --mode client --out generated/pcloud-client.ts`, then update the three workspace-local skills at `.agents/skills/pcloud-{cli,client,types}/SKILL.md` to the new tool count. These are gitignored — they are regenerated per-developer.
