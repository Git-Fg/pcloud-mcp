## pCloud MCP: agent rules

- API quirks, token provenance, and endpoint limitations live in `docs/pcloud-notes.md`. Read it before asserting anything about pCloud behavior.
- Authentication: non-OAuth. `PCLOUD_ACCESS_TOKEN` is read from env and sent as `?access_token=` per the HTTP/JSON protocol. `PCLOUD_ACCESS_ID` is the application/access id, not a credential. `PCLOUD_API_SERVER` defaults to `eapi.pcloud.com` (EU). All requests hit `https://<PCLOUD_API_SERVER>/<method>` (default `https://eapi.pcloud.com/<method>`); override the server via `PCLOUD_API_SERVER` (see `src/core/config.ts`). Every response carries `result` (`0` = success, non-zero = error surfaced as MCP `isError`).
- Tools registered: the `tools` array in `src/core/tools/index.ts` is the authoritative list (name, `ToolMeta`, handler, output schema); enumerate it rather than counting, because `registerPcloudTools` is a single loop over that array and `registerTool` appears exactly once (inside the loop). `index.ts` imports each tool's `ToolMeta` (title/description/annotations/inputSchema) from its handler file. `deletefile` and `deletefolder` are intentionally separate. `resolve` wraps `stat` to give `{fileid|folderid, isfolder}`. `find` is a BFS over `listfolder` (pCloud exposes no documented search endpoint). `copyfile`/`copyfolder`/`downloadfile` are server-side (no bytes cross this server).
- Run `bun run typecheck && bun run build && bun test && bun run lint` after any change to `src/core/tools/*` or `src/mcp/*`.
- Regenerate mcporter artifacts after tool-surface changes. The tracked codegen definition is `config/mcporter.gen.json` (object-form command, repo-relative `cwd`); `config/mcporter.json` is the runtime config (string + args form) read by `emit-ts`. Codegen shape changes go in `config/mcporter.gen.json`, not in this file or in prose docs: `PATH="$PWD/node_modules/.bin:$PATH" mcporter generate-cli --server config/mcporter.gen.json --output pcloud.ts` + `bun build pcloud.ts --target=bun --outfile=pcloud-cli.js --minify` + `PATH="$PWD/node_modules/.bin:$PATH" mcporter emit-ts pcloud --config config/mcporter.json --mode types --out generated/pcloud-types.d.ts` + `PATH="$PWD/node_modules/.bin:$PATH" mcporter emit-ts pcloud --config config/mcporter.json --mode client --out generated/pcloud-client.ts`. `pcloud.ts` and `pcloud-cli.js` are tracked build artifacts at the repo root (regenerated by the pre-commit hook: `pcloud.ts` + `pcloud-cli.js` always; the emit-ts outputs in `generated/` only when `REGEN_ALL=1`). Both CLI artifacts MUST stay at the repo root: the embedded stdio server command spawns `bun run src/index.ts` with a cwd resolved relative to the script's own directory, so a bundle placed in a subdirectory cannot start the server. The collapse condition and retest recipe for the dual-config split live in `CONTRIBUTING.md` § "Dual-config watch". The tracked skills at `.agents/skills/pcloud-{cli,client,types,troubleshooting,recovery,sharing-security,reorganize}/SKILL.md` are part of the repo; they are not gitignored.
- MCP registration is machine-local via `.mcp.json` (gitignored) at the repo root (and `.kimi-code/mcp.json` locally, which is gitignored). A template ships as `.mcp.json.example`.
- A local pre-commit hook regenerates `pcloud.ts` and `pcloud-cli.js` before each commit (tracked copy at `.githooks/pre-commit`; activate with `git config core.hooksPath .githooks`); set `REGEN_ALL=1` to also rebuild the emit-ts outputs in `generated/`. Run `chmod +x` if it ever loses its executable bit.
- Live verification: `bun run scripts/live-mcp-e2e.ts` (requires `PCLOUD_ACCESS_TOKEN`; creates a temp folder + file, exercises upload/getfilelink/deletefile/deletefolderrecursive, cleans up).
- Transport: stdio by default (`bun run dev`); HTTP via `MODE=http` on `127.0.0.1:3000` with a DNS-rebinding host allowlist, CORS deny-by-default, and a bearer gate for non-loopback binds. See `src/mcp/http.ts`.
- `uploadfile` and `uploadtolink` share `src/core/http/upload.ts` for chunked reads and progress; progress notifications echo the request's `_meta.progressToken` and are labeled `read`/`uploading`. `readfile` streams the download and cancels at `maxBytes`; the signed download URL is never returned. `uploadfile` replaces an existing same-named file in the target folder unless `renameifexists` is set, and concurrent uploads into one folder race on name allocation — serialise uploads that share a destination folder. `listfolder`'s `recursive` walks the subtree client-side (pCloud rejects the server-side flag); every returned entry carries its full path.
- `extractarchive` runs server-side for ~2s; a `finished=false` response carries a `progresshash` that only the returned `hostname` can poll.
